# M02 — Resilience boundary validation

## Why

`resilience.py` already implemented retry-with-backoff, a circuit breaker and
Pydantic-validated LLM calls with a deterministic fallback, and the README
claimed "deterministic fallback on any failure". The tests around it did not
back that claim: they covered one bad output, a valid output, and a breaker
whose open window was manipulated by writing the private `_open_until` field.
There were no timeouts, rate limits, repeated provider failures, no controlled
clock, and no comparison between the plain orchestrator and the optional
LangGraph path.

M02 adds the adversarial tests, makes the time source injectable so the
circuit can be tested without sleeping, and documents exactly what survives a
provider failure and what does not.

## What changed

`src/multi_agent_optimizer/resilience.py`:

- `CircuitBreaker(..., clock=None)` — the clock defaults to `time.monotonic`,
  so production behaviour is unchanged, but tests can advance time
  deterministically.
- `CircuitBreaker.failure_count` — read-only observability of consecutive
  failures since the last success.
- `retry_with_backoff(..., sleep=None)` — the sleeper defaults to
  `time.sleep`, so tests can record or skip delays.
- Removed two pre-existing suppressions (`# type: ignore[misc]`,
  `# noqa: BLE001`) and the redundant `(Exception, ValidationError)` catch
  (`ValidationError` is an `Exception`). Behaviour is unchanged.

`tests/test_m02_resilience.py` — 27 tests, no network and no paid calls.

## The resilience pipeline

```
provider ─▶ parse_validated ─▶ Pydantic schema ─▶ result
              ▲     │
              │     └─ invalid JSON / schema ─┐
              │                               ▼
       retry (2 attempts) ── failure ──▶ circuit breaker ── threshold ──▶ open
              │                               │                        (skip calls)
              └──────────── success ─────────┘                              │
                                                                     reset window
                                                                          │
                                                                   probe call
```

| Failure injected | What happens | Observable result |
|---|---|---|
| Invalid JSON, truncated JSON, wrong shape, empty output, multiple objects | `parse_validated` raises; retried once; breaker counts one failure | documented fallback value; exactly 2 provider calls |
| Valid JSON in prose | extracted and validated | enriched result; 1 call |
| `TimeoutError` | retried once, then breaker failure | fallback; 2 calls |
| `HTTPError 429` (rate limit) | retried once, then breaker failure | fallback; 2 calls |
| `ConnectionResetError` | retried once, then breaker failure | fallback; 2 calls |
| 3 consecutive logical failures | breaker reaches its threshold | `is_open` true, `failure_count` 3; later calls raise `CircuitOpenError` inside `safe_llm_json` and take the fallback without touching the provider |
| Reset window elapses | breaker closes for a probe | a successful probe resets `failure_count` to 0; a failed probe reopens for another window |

## Fallbacks per agent

| Agent | Schema | Fallback when the provider fails |
|---|---|---|
| `SchedulerAgent` | `_Notes` | the deterministic schedule table (same text as `NoopLLM`) |
| `RiskAgent` | `_Note` | no `llm-note` risk; the CPM-derived risks are unchanged |
| `OptimiserAgent` | `_Thought` | no `llm-note` suggestion; the CPM-derived suggestions are unchanged |

The fallback values are constructed before the call, so a failure cannot
produce an empty or partial enrichment that looks like a real answer.

## Why scheduling facts cannot change

`MultiAgentOptimizer.optimize` runs `schedule(tasks)` before it constructs the
LLM call path, and the agents only read the resulting `Schedule`. They never
feed anything back into it. Tests assert, for timeouts, rate limits, repeated
failure, invalid output and wrong-schema output:

- `project_duration`, `critical_path`, `topological_order` and every task's
  `early_start`/`early_finish`/`late_start`/`late_finish`/`slack` are identical
  to a `NoopLLM` control run;
- the deterministic risk and suggestion entries are identical;
- the narrative is identical (the table fallback);
- the input project dictionary is not mutated;
- an invalid project raises `ProjectError` before any provider call.

## Core vs graph path

`tests/test_m02_resilience.py` compares `MultiAgentOptimizer(...).optimize()`
with `run_langgraph(...)`:

- deterministic mode: duration, critical path, narrative, risks and
  suggestions are equal;
- failing provider: the graph path preserves the same duration, critical path,
  narrative and deterministic enrichment, and adds no LLM notes.

## Acceptance mapping

| Requirement | Where |
|---|---|
| Invalid structured output | `test_invalid_structured_output_falls_back`, `test_valid_output_wrapped_in_prose_is_extracted`, `test_parse_validated_rejects_invalid_output_directly`, `test_provider_failures_cannot_alter_scheduling_facts[invalid_output/wrong_schema]` |
| Timeouts | `test_provider_errors_fall_back_after_two_attempts[timeout]`, `[...][timeout]` optimizer case |
| Rate limits | `... [rate_limit]` cases, `test_scheduler_falls_back_to_the_same_narrative_table` |
| Repeated provider failure | `test_repeated_failure_opens_each_agents_circuit_then_recovers`, `[repeated_failure]` optimizer case |
| Circuit opening/recovery with controlled time | `test_circuit_opens_after_threshold_and_skips_calls`, `test_failed_probe_after_reset_reopens_the_circuit`, `FakeClock` |
| Core vs optional graph path | `test_graph_path_matches_core_outputs_when_deterministic`, `test_graph_path_preserves_scheduling_facts_under_provider_failure` |
| Failures cannot silently alter valid scheduling facts | `_assert_same_schedule` applied to 5 failure modes plus the open-circuit and recovery runs |
| Recovery observable | `failure_count`, `is_open`, provider calls skipped while open, LLM enrichment (`deterministic=False`) returning after the probe |
| Documented fallback works | the table above plus the fallback assertions |

## Limits / remaining weaknesses

- The circuit breaker is **in memory and per agent instance**. A new process,
  a new `MultiAgentOptimizer`, or each `run_langgraph` call starts with a
  closed circuit. `build_graph` creates fresh agents per invocation, so the
  graph path does not remember failures across runs.
- `safe_llm_json` retries **every** exception the same way; it does not
  distinguish rate limits (which may deserve longer backoff) from schema
  errors (which may deserve a different prompt) or timeouts.
- Backoff is deterministic (`base_delay * factor**i`) with no jitter, so many
  callers can retry in lockstep.
- The library does not impose its own request timeout; `OpenAICompatibleLLM`
  passes `timeout=60` to `urllib.request.urlopen`. A caller-supplied client
  must implement its own timeout.
- `extract_json_object` takes the substring from the first `{` to the last
  `}`; multiple JSON objects in one reply are merged and fail validation
  (tested). It does not attempt to pick the right object.
- The fallback for `SchedulerAgent` is the full schedule table; it is
  deterministic but not prose. Callers that require an LLM-written narrative
  must detect `NoopLLM`/fallback mode themselves — there is no status flag on
  the result.
- The graph path executes `schedule()` once per node (three times per run).
  Results agree, but it is redundant work.

## Alternatives considered

- **Patch `time.monotonic` in tests.** Rejected: it mutates process-global
  time and makes tests order-sensitive. An injected clock keeps the
  production default while making time a parameter.
- **Sleep for real in the recovery test.** Rejected: slow, flaky, and it does
  not prove the boundary (exactly `reset_seconds`).
- **Retry schema errors forever / no retry for provider errors.** Rejected:
  one retry covers transient network failures without multiplying load; both
  classes still fall back.
- **Fail the request when the provider fails.** Rejected by the product
  design: the deterministic answer is the deliverable, the LLM is enrichment.
  The README now states that boundary explicitly.
