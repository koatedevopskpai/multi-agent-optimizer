# M01 — Optimiser validation beyond two golden cases

## Why

Before M01 the eval gate had two valid golden cases and `tests/test_cpm.py`
covered the happy path plus a two-node cycle, an unknown dependency, an empty
project and a negative duration. That left several classes of input untested,
and inspection of `cpm.py` turned up defects the old suite could not see:

| Defect (before M01) | Consequence |
|---|---|
| `isinstance(duration, int)` accepts `True`/`False` | a boolean duration was scheduled as 1/0 |
| duplicate dependency ids accepted | silent double counting in the indegree map |
| a non-mapping task body raised `TypeError` | not the documented `ProjectError` |
| a non-string task id raised `TypeError` on `.strip()`-free paths / produced odd `Task` ids | contract not fail-closed |
| `_detect_cycle` was a recursive DFS | `RecursionError` on a valid chain of ~1000+ tasks visited deepest-first |
| backward pass rescanned every task per node | O(V²) on large valid schedules |
| Kahn's algorithm had no post-condition | a cycle bug could silently return a partial order |
| golden cases could only be valid projects | invalid input was only tested in unit tests |

## What changed

Code (`src/multi_agent_optimizer/cpm.py`):

1. **Input validation** in `build_tasks`: the project must be a mapping; task
   ids must be non-empty strings; each task body must be a mapping; `duration`
   must be a genuine non-negative `int` (booleans rejected); dependencies must
   be a list of non-empty strings with no duplicates and no unknown ids. Every
   failure raises `ProjectError`, never `TypeError`.
2. **Iterative cycle detection**: `_detect_cycle` now uses an explicit stack of
   `(node, dependency index)` frames inside a tri-colour DFS. The cycle path is
   still reported (`A -> B -> A`).
3. **Post-condition in `topological_order`**: if Kahn's algorithm emits fewer
   nodes than the graph contains, it raises `ProjectError` rather than
   returning a partial order. This branch is defensive and unreachable through
   `schedule()` because `_detect_cycle` runs first; it is the one uncovered
   line in `cpm.py`.
4. **O(V+E) backward pass**: the dependents list is built once and reused,
   replacing `[c for c in tasks if node in tasks[c].dependencies]`.
5. **`start` validation** rejects booleans as well as non-ints/negatives.

Behaviour that did **not** change: the schedule math, `ProjectError`'s base
class (`ValueError`), the meaning of `start` (an offset; `project_duration` is
the end timestamp, so `schedule(project, start=10).project_duration` is the
chain length plus 10), and `critical_path` (see limits below).

Evaluation (`evals/evaluate.py`, `evals/golden_cases/`):

- Golden cases grew from 2 to 11: disconnected components, zero durations,
  multiple equal critical paths, a start offset, a 60-task valid schedule, and
  four invalid cases (cycle, unknown dependency, negative duration, duplicate
  dependency) declared with `expected_error`.
- Every valid case is checked three ways: expected duration + critical set,
  **scheduling invariants**, and an **independently written baseline**.
- `evals/EVAL_REPORT.md` is generated output; it is now ignored and untracked
  so running the gate does not dirty the tree.

Tests (`tests/test_cpm_validation.py`, 67 tests):

- invariant helper and independent baseline;
- 25 seeded random DAGs compared against the baseline;
- cycles (2-node, self, 6-node), cycles in disconnected components, cycle path
  contents, insertion-order independence;
- 16 malformed projects, 3 invalid `start` values;
- disconnected activities, zero durations, equal/unequal multiple critical
  paths, disjoint critical paths;
- a 2000-task chain in both insertion orders (the deepest-first one defeats a
  recursive DFS) and a 500-task wide schedule;
- determinism across calls and dict orderings;
- `MultiAgentOptimizer(llm=NoopLLM())` produces the same schedule fields as
  `schedule()`.

## Invariants checked

For every valid schedule `assert_invariants` / `invariant_errors` verify:

- the schedule has exactly the project's tasks and the topological order is a
  permutation in which every dependency precedes its dependent;
- `early_start >= start`, `early_finish == early_start + duration`;
- `early_start >= max(early_finish of dependencies)`;
- `late_finish == late_start + duration`, `late_finish <= project_duration`,
  `late_finish <= late_start` of every dependent;
- `slack == late_start - early_start >= 0`, and `is_critical == (slack == 0)`;
- `project_duration == max(early_finish)`;
- `critical_path` equals the sorted set of zero-slack tasks, is non-empty, and
  its first task starts at `start` while its last finish is `project_duration`.

## Independent baseline

The baseline does **not** reuse the forward/backward passes. For each task it
memoises a top-down recursion:

- `earliest_finish(t) = duration(t) + max(earliest_finish(d) for d in deps)`
  (longest weighted path ending at `t`);
- `tail(t) = duration(t) + max(tail(c) for c in dependents)`;
- `late_start(t) = project_end - tail(t)`, `slack = late_start - early_start`.

Both algorithms derive the same quantities by different routes (path
enumeration vs. ordered passes), so agreement is meaningful. The baseline is
used on four hand-checkable graphs, 25 seeded random DAGs, and every valid
golden case.

| Large valid schedules | `test_long_chain_does_not_hit_the_recursion_limit` (2000 tasks, both insertion orders), `test_wide_schedule_with_one_long_tail` (500 tasks), `case_011` (60 tasks) |
| Scheduling invariants | `assert_invariants` in the test module; `invariant_errors` in the eval gate |
| Independent baseline | baseline comparison on 4 examples, 25 random DAGs, all valid golden cases |
| Deterministic with model disabled | `test_model_layer_disabled_matches_the_deterministic_core`, `test_schedule_is_deterministic_across_calls_and_insertion_orders`; the eval gate makes no model calls |

## Limits / remaining weaknesses

- `duration` is an integer in an unspecified unit. Fractional durations are
  rejected by design, not rounded.
- `critical_path` is a **sorted list of zero-slack task ids**, not an ordered
  walk. When several critical paths exist, all of their tasks appear. Callers
  that need one ordered walk must reconstruct it from the schedule.
- Duplicate task ids cannot exist in a Python dict, so that "impossible"
  input is unrepresentable rather than validated.
- The engine models only finish-to-start dependencies with zero lag. No
  resources, calendars, leads/lags, PERT estimates or maximum durations.
- Large-graph checks are correctness checks, not benchmarks. The forward and
  backward passes are O(V+E); `_detect_cycle` is O(V+E) apart from one
  `list.index` when a cycle is found.
- Recursion remains in the test/eval *baseline* (bounded to small graphs); the
  production engine no longer recurses.
- The defensive post-Kahn check is not reachable through the public API, so it
  is not covered by a test. Removing it would raise coverage to 100% at the
  cost of defence in depth.

## Alternatives considered

- **Keep the recursive DFS and raise the recursion limit.** Rejected: it
  moves the failure threshold rather than removing it, and a library should
  not mutate process globals.
- **Accept booleans as durations (`int` subclass).** Rejected: `True` silently
  becomes a 1-day task; fail closed instead.
- **Reject duplicate dependencies or de-duplicate silently.** De-duplicating
  hides a malformed plan; the engine raises so the caller fixes the source.
- **Third-party CPM library.** Rejected: the project is deliberately
  dependency-light and the math is small enough to own and test.
- **Compare the engine against itself** (e.g. re-run `schedule`). Rejected: it
  cannot detect a shared bug. The baseline is a separate implementation.
